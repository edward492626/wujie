# wujie 微前端内存泄漏排查：经验教训

> 背景：主应用（xr-main-vite）关闭 wujie 子应用 tab 后，整棵子应用 DOM 树（百万级节点）无法 GC。前后经历 5 轮快照取证、发现 **5 个相互独立的根因**，全部修复后泄漏归零。本文记录踩过的坑与可复用的经验，工具用法见 [scripts/heap-analysis/README.md](../scripts/heap-analysis/README.md)。

---

## 一、五个根因的技术教训

按发现顺序排列。共同点：**每一个单独看都"不太可能"，叠加起来才是完整泄漏链**。

### 1. Vue2 钩子名在 Vue3 下静默失效（最冤）

- **现象**：`bus.$onAll(handleEmit)` 注册后永不清理，每个关闭的 tab 泄漏一个组件实例闭包。
- **真相**：wujie-vue3 组件清理挂在 `beforeDestroy`（Vue2 钩子名）。Vue3 改名为 `beforeUnmount`/`unmounted` 后，**旧钩子名不报错、不警告、静默跳过**。
- **教训**：
  - 任何 Options API 组件库升级 Vue3，必须 grep 全量钩子名（`beforeDestroy`/`destroyed`），这类失效是静默的，功能测试发现不了，只有泄漏测试能暴露。
  - 堆取证指纹：残留回调是 `handleEmit.bind(JSProxy)`——Vue3 Options API 会把 methods 自动 bind 到组件实例代理，`native_bind` + JSProxy 是铁证。

### 2. async destroy 与 startApp 复用分支的竞态（最诡异）

- **现象**：console 出现 `beforeUnmount → SOSO app mount → afterUnmount`——销毁三连中间夹着一次重挂。
- **真相**：`startApp` 复用分支在 `await sandbox.unmount()` 处让出微任务；恰好此时用户关 tab，destroy 同步跑完（iframe 已摘除）；微任务恢复后 startApp 继续 `active()` 把已摘除的 iframe **重新 append 回容器**并 `__WUJIE_MOUNT()` 僵尸复活。
- **教训**：
  - async 函数里每个 `await` 都是一个竞态窗口，恢复后**必须重新校验世界状态**（本例是 `sandbox.destroyed`），不能信任 await 之前的检查。
  - 日志时间线是竞态排查的第一手段：反常的顺序（unmount 日志里夹 mount）直接暴露交错点。

### 3. destroy 中途异常夭折（最老实）

- **现象**：注册表已清（destroy 前半执行了）但 iframe 仍 attached（后半没执行）。
- **真相**：`clearChild(this.el)` 与 Vue 的并发 DOM 卸载操作同一子树抛 NotFoundError，同步异常中断 destroy，后面的 `removeChild(iframe)` 被跳过。
- **教训**：
  - **销毁函数必须分段异常隔离**：各清理段（el 清理 / 事件解绑 / iframe 摘除）之间 try/catch 隔离，保证关键收尾动作（removeChild）必达。清理代码里的异常应该吞掉而不是传播——销毁路径上"部分成功"远好于"中途夭折"。
  - 快照取证技巧：`dump` 看 iframe `detached` 标志 + 注册表残留形态，可以精确定位 destroy 死在第几段。

### 4. V8 hidden class 跨 realm 钉死（最隐蔽，JS 引用分析全失效）

- **现象**：所有 JS 引用泄漏修完，快照里仍有 2 个 attached iframe，`ret` 追链追不出任何 JS 引用者。
- **真相**：任何 JS 对象的 hidden class **固有引用其创建时的 NativeContext（realm）**。子应用里加载的 EFX 组件库自带一份 wujie 副本，其模块级 bus 向共享 `appEventObjMap` set 了一个**创建于 iframe realm 的空对象 `{}`**。副本随 iframe 死亡后无人清这个 entry——一个**空对象**把整个子应用 realm（iframe + 百万 DOM 节点）永久钉死。
- **教训**：
  - **空对象 ≠ 无害**。跨 realm 存对象时，对象本身就携带 realm 引用（hidden class → NativeContext），与对象内容无关。
  - 识别指纹：主 realm 对象的 `__proto__` label 带 URL 标注，异 realm 创建的对象没有——`heap.mjs events` 命令已内置此检测。
  - 这类泄漏在 DevTools Retainers 里**看不见**（JS 引用是空的），必须看 `map → native_context` 内部边。

### 5. 多份 wujie 副本 + 共享全局表（架构层）

- **真相**：wujie 把 `appEventObjMap` 通过 `window.__WUJIE_INJECT` 跨 realm 共享；任何在子应用里再加载一份 wujie 的组件库（本例 EFX）都会往这张表写入，且**副本销毁时无人负责清自己的条目**。
- **教训**：
  - 微前端架构里"宿主与子应用各自打包同一个库"是泄漏温床：全局单例（Map/bus）会被多副本交叉写入，责任边界模糊。要么共享依赖（externals），要么宿主在 destroy 时兜底清理全局表。
  - 排查口诀：快照里出现**多个时间戳 id 的 bus entry** = 存在多副本，立刻排查是哪个组件库带进来的。

## 二、走过的弯路（诚实记录）

| 弯路 | 教训 |
|---|---|
| 用正则扫线上 34 个 chunk 得出"线上没有 wujie"的错误结论——实际漏抓了二级 chunk 和 hash 含 `-` 的文件名，且 wujie 打在更深的 `efDialogForm-*.js` 里 | **对"没找到"的结论要保持怀疑**：先验证扫描方法本身（用一个确定存在的字符串做阳性对照） |
| shell `node -e "..."` 内嵌脚本多次因转义/编码失败，grep 中文注释返回 0 误判为"补丁没生效" | 一次性脚本直接写临时文件跑，别在 shell 转义地狱里挣扎；验证代码特征用不会被压缩/转码改写的标识符 |
| 把两条 `beforeUnmount` 日志误读为"组件 unmount 执行了两遍"，差点往 keep-alive 方向排查 | **同格式日志可能来自不同函数**（Vue 钩子 vs wujie 生命周期钩子）。下结论前先对一下打包产物里到底是哪两个函数 |
| 最初怀疑 EFX 没发补丁，花时间验证部署链路 | 快照里的**字符串表可以直接验证线上代码指纹**（`strings` 命令搜补丁特有标识符），比推断部署状态快得多 |
| jest 报错行号指向已删除的代码，白改一轮测试 | 转换缓存未失效，先 `--clearCache` 再怀疑代码 |
| 单次开关验证竞态修复 | 竞态是概率命中的，验证要连续开关多次拍快照看指标是否线性增长 |

## 三、有效的方法论（下次直接复用）

1. **三快照定差异**：基线 / 打开子应用 / 关闭子应用，`byname + cmp` 找只增不减的类别。不要跳过基线——很多"增长"是框架正常驻留（ScopeInfo/FeedbackMetadata 等 V8 内部对象，几百 KB 级，不是泄漏）。
2. **快照即取证现场**：
   - `strings` 验证线上跑的代码版本（补丁生效了吗？）——比看部署系统快；
   - `dump` 看 detached 标志——区分"仍 attached"（destroy 没摘 DOM）和"detached 但被引用"（JS 闭包钉住）；
   - `ret` 追保留链——注意排除 DevTools 伪影（`nodevtools` 复核）。
3. **日志时间线还原竞态**：反常顺序（销毁日志里夹挂载日志）= 交错点。给关键生命周期加 console.log 是值得的。
4. **注册表审讯直读死因**：`sandbox` 命令看 idToSandboxMap 残留形态（实例存活 / 仅 options 残留 / 全空），能直接判断 destroy 执行到哪一段。
5. **JS 引用追不出来时，怀疑引擎层**：hidden class、Global handles、Blink wrapper 表——这些在 DevTools Retainers 里不可见，需要看 `map → native_context` 等内部边。
6. **修复用单测固化**：竞态场景写成确定性测试（Promise gate 控制让出时机），7 条测试锁住 3 个竞态窗口，防止未来回归。

## 四、工程与流程教训

1. **修复必须全链路验证**：源码 → yalc publish → `yalc add` → patch 脚本 → `node_modules` → dist 产物 → 线上产物 → 快照 strings 指纹。**任何一环断了，后面全白做**。本轮就发生过 patch 生成了但 esm 产物没更新的情况（好在验证时发现）。
2. **多项目补丁必须同步**：wujie 修复打在两个项目的 pnpm patch 里（主应用 + EFX）。只发主应用 = EFX 里还是旧代码继续泄漏。修复跨包问题时列一张**受影响项目清单**逐个确认。
3. **工具链升级会破坏脚本**：pnpm 11 把 `patchedDependencies` 从 package.json 迁到 pnpm-workspace.yaml，旧清理脚本只清 package.json 导致 ENOENT。CI 里的胶水脚本要在工具升级后回归一遍。
4. **一次只改一个变量**：多轮修复验证时，主应用和 EFX 分别部署——否则无法归因"还有泄漏"是哪个产物的问题。
5. **验收要量化基线**（详见 heap-analysis README 末节）：iframe 归零、ShadowRoot 回基线、appEventObjMap 无空 entry/异 realm 告警。没有量化标准的"感觉好了"不可信。

## 五、Quick Check 清单（下次排查直接过）

```text
□ 三快照（基线/打开/关闭）已拍，diff 只增不减的类别已锁定
□ strings 验证线上代码含修复指纹（别信部署状态，信快照）
□ iframe detached 状态确认：attached = destroy 没摘 DOM；detached = JS 引用钉住
□ ret 保留链已追，DevTools 伪影已用 nodevtools 排除
□ sandbox 审讯：注册表残留形态 = destroy 执行到哪一段
□ events 审讯：时间戳 entry 数（= wujie 副本数）、空 entry、异 realm 告警
□ 日志时间线：销毁三连（beforeUnmount/unmount/afterUnmount）之间是否夹入 mount
□ 组件库钩子名 grep：beforeDestroy / destroyed（Vue3 下静默失效）
□ destroy 各清理段异常隔离，removeChild(iframe) 必达
□ async 函数每个 await 恢复点重新校验销毁状态
□ 所有打包了该库的项目（主应用/组件库 remote）补丁已同步
□ 连续开关 10 次后指标无线性增长

```
